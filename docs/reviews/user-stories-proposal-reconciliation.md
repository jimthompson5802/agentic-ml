## Findings and proposed corrections

### R-01 — Resolved: profiling and split manifests belong to Slice 2 / phase 2

Original finding (High): Slice 1 required profiling and split manifests while proposal §11 scheduled them in phase 2.

Approved product-scope decision: retain detailed profiling and train/validation/protected-test splits in phase 2 and move the corresponding story criteria into Slice 2. Slice 1 delivers reproducible extraction, basic validation and review, recorded execution, and source-data/run restoration.

Applied corrections:

- Slice 1 retains US-12-AC-01 and adds US-12-AC-05 for approval of basic validation results.
- Slice 2 now contains US-12-AC-02–04: detailed profiling, versioned split manifests, and assessment/split approval before dependent feature or modeling work. Existing criterion IDs are preserved.
- Slice summaries, entry conditions, design criterion mappings, and §11 deliverables/exit criteria now reflect this boundary. Source dataset versioning/restoration is required in Slice 1; split manifests are required when introduced in Slice 2.

Scoped reconciliation: profiling and split delivery timing now aligns. This resolves R-01 only; R-02 addresses controls separately, and the restoration, recovery, and feature-comparison findings remain open.

### R-02 — Resolved: controls accompany the capabilities they govern

Original finding (High): the implementation table assigned gates to phase 5 without explicitly committing to the controls required by earlier slices.

Clarification applied: controls are harness-enforced approvals, access restrictions, budgets, independent artifact/result validation, and boundaries on agent revisions. They determine what an experiment may do and whether its results are accepted.

- §9 Governance defines controls with a concrete dataset-access/runtime example.
- §11 commits each phase to its required controls: execution/extraction authorization, access restrictions, limits, and independent artifact checks in phase 1; assessment/split approval and training-only fitting in phase 2; baseline approval and protected final evaluation/review in phase 3; approved, bounded agent iteration in phase 4.
- Phase deliverables and exit criteria express these commitments. Phase 5 coordinates existing controls across the durable workflow and recovery.
- ADR-006 retains the pending isolation implementation decision while requiring enforcement before each governed capability is delivered. Early developer-driven approvals must still be recorded and enforced.

Scoped reconciliation: the early-delivery commitment is now explicit. This resolves the documented sequencing issue, without asserting that controls are implemented or that the pending isolation mechanism has been selected.

### R-03 — Resolved: external coding assistance and harness plan resolution are distinct

Original finding (Medium): Slice 1 required a versioned plan without an agent, while proposal §8 assigned delegated-choice resolution to an agent and §11 deferred agent integration to phase 4.

Approved clarification: developers may use external coding assistants such as Codex, GitHub Copilot, or Claude Code to prepare experiment inputs and code from Slice 1. The harness has no agent dependency for validating, recording, or executing supplied inputs. Phase 4 adds harness-managed agent proposals and iteration.

- The Slice 1 description clarifies that external coding assistance is allowed while an agent is not required.
- Proposal §4 distinguishes the integrated-agent workflow from earlier developer-supplied inputs and notebooks.
- §8 assigns input validation and versioned plan recording to the harness, including effective decisions, defaults, source references, checksums, and approval evidence. Unresolved choices block dependent execution; delegated decisions require approval before use.
- §11 phase 1 explicitly delivers plan validation and recording without an agent dependency. Phase 4 proposals use the same validation and approval path.

Scoped reconciliation: US-03-AC-03–04 are now supported by an explicit mechanism. R-03 is resolved as document alignment; this does not assert implementation or resolve R-04–07 or D-01.

### R-04 — Resolved: evidence capture and verified restoration are explicit

Original finding (Medium): [US-13-AC-03–04](../specs/user-stories.md#us-13-ac-03) and [US-27-AC-01–04](../specs/user-stories.md#us-27-ac-01) required verified dataset restoration, second-machine replay of exact source including uncommitted changes, output checks, and explicit missing-input failures in Slice 1. The design captured artifacts and stated reproducibility intent without specifying how to assemble, verify, and execute them for replay.

Approved correction applied in proposal [§9 Run evidence capture and restoration](../specs/agentic-ml-harness-design.md#run-evidence-capture-and-restoration), §10 acceptance fixtures, and §11 phase 1:

- Schema-versioned manifests connect immutable source/configuration bundles, pinned environment evidence, DVC dataset identities, execution settings, applicable guidance/approval references, and result checks. MLflow and DVC retain their existing storage responsibilities.
- Capture and persist required input evidence before execution, then execute the frozen source in a separate execution directory. Preserve modified and required untracked files; later working-tree edits cannot change the submitted run.
- Restore the pinned harness, locked environment, recorded source, and dataset content with checksum verification. Missing or mismatched required inputs fail explicitly without substitution; current access and execution authorization still apply.
- Record reproduction as a new run linked to the original manifest and independently compare outputs using the original declared checks/tolerances. Preserve available evidence for unsuccessful runs as well.
- Phase 1 provides agent-free restoration and a clean second-machine demonstration with an uncommitted notebook edit and required untracked helper, plus negative fixtures for missing/corrupted inputs.

Scoped reconciliation: US-13-AC-03–04 and US-27-AC-01–04 now have compatible architectural support in their required slice. R-04 is resolved as document alignment; implementation and passing tests are not asserted. Manifest serialization and CLI/API signatures remain pending. R-05 submission/recovery reconciliation and R-07 training-checkpoint restoration are not resolved by this lifecycle. User stories and criterion identifiers are unchanged; other findings have not been re-reviewed in full.

### R-05 — Resolved: durable submission identity and duplicate-free recovery are explicit

Original finding (Medium): [US-25-AC-01–02](../specs/user-stories.md#us-25-ac-01), [US-26-AC-13](../specs/user-stories.md#us-26-ac-13), and [US-29-AC-07](../specs/user-stories.md#us-29-ac-07) require recovery without duplicated completed runs, lost budget consumption, or detached producer provenance. Durable state and agent-resumption intent did not sufficiently define runner/tracking reconciliation or ambiguous submissions.

Approved correction applied in proposal [§8 Submission identity and recovery contracts](../specs/agentic-ml-harness-design.md#submission-identity-and-recovery-contracts), [§9 Recovery and reconciliation](../specs/agentic-ml-harness-design.md#recovery-and-reconciliation), §10 fixtures, and §11 phase 5:

- Persist intent, stable task/attempt submission identity, approved configuration/input-manifest identity, approvals/guidance, and budget reservation before submission. Runner submission binds the key durably before execution; identical retries return the existing run, while different inputs conflict.
- Reconcile workflow records, runner status, and MLflow evidence before new work. Reuse verified completed runs, monitor active runs, and retry definitively unaccepted submissions with the original key. Unknown/conflicting status or insufficient completion evidence enters review without blind resubmission.
- Preserve consumed budgets without double counting; retain uncertain reservations. Preserve original producer provenance, dataset lineage, authorization history, and decisions permitting reuse. Restart does not authorize additional work or bypass gates.
- Require exclusive recovery ownership with stale-owner rejection and retry-safe tracking/finalization. Failed/cancelled execution retries are separately linked attempts subject to scope and remaining budgets; explicit reproduction remains a new linked run.
- Phase 5 defines concrete persistence, schemas, ownership/fencing, and reconciliation mechanisms and verifies interruption, lost acknowledgements, tracking outages, concurrent recovery, accounting, provenance, and approval preservation.

Scoped reconciliation on 2026-10-28 against Git revision `b100d9251182b2dae2303370d40cbeedfbbb31cd` plus this approved working-tree update: the working tree was clean before the correction. US-25-AC-01–02, US-26-AC-13, and US-29-AC-07 now have compatible architectural support in their required slices. This resolves R-05 as document alignment; implementation and passing tests are not asserted. Storage technology, exact serialization, and transaction/fencing mechanisms remain implementation decisions subject to the defined contract. User stories and criterion identifiers are unchanged. Review was limited to R-05 and its runner, evidence-manifest, agent-resumption, governance, and phase-delivery dependencies; R-06–07 and D-01 remained open at that stage. The subsequent R-06 correction below resolves R-06 and D-01; other findings were not re-reviewed in full.

### R-06 — Resolved: Slice 2 compares predictive performance using a fixed reference estimator

Original finding (Medium): US-14-AC-03 required feature comparison without specifying whether it measured data quality or predictive performance, while broader model training was scheduled for Slice 3.

Approved product decision: “better” means improved predictive performance. US-14-AC-03 retains its ID and now compares candidate feature sets against a fixed approved baseline feature set using the same fixed approved reference estimator/settings, metric, and split protocol. The metric direction determines improvement; valid comparisons also record ties and regressions.

Applied corrections:

- Story Slice 2 summary, narrative, and US-14-AC-03 include minimal training/evaluation for predictive feature comparison; broader model experimentation remains in Slice 3.
- Proposal §§4–5 authorize this limited training/evaluation within feature engineering; §7 defines fixed comparison inputs, training-only fitting, validation-only scoring, protected-test isolation, approvals, budgets, independent checks, and reproducible run evidence.
- §10 fixtures and §11 phase 2 deliverables/exit criteria verify predictive comparison and its controls. Phase 3 retains broader model experimentation, algorithm selection, hyperparameter search, and authorized final evaluation.

Scoped reconciliation on 2026-10-28 against Git revision `fe48f81530dbbffd571a5689d9e2f63394cbed12` plus this approved working-tree update: the working tree was clean before the correction. US-14-AC-03 now has compatible design support in Slice 2. R-06 and D-01 are resolved as document alignment; implementation and passing tests are not asserted. Review was limited to R-06 and its feature-engineering, evaluation, control, provenance, and phase-sequencing dependencies. R-07 remains open; other findings were not re-reviewed in full.

### R-07 — Resolved: checkpoint restoration and cancellation preservation are explicit

Original finding (Medium): US-19-AC-02–03 require restorable captured checkpoints and preservation on cancellation. Checkpoint capture and final-model persistence alone did not define a usable checkpoint restore path or cancellation preservation.

Approved correction applied:

- Proposal [§8 PyTorch checkpoint restoration](../specs/agentic-ml-harness-design.md#pytorch-checkpoint-restoration) requires a documented restore path through the supplied or built-in model implementation. The implementation defines checkpoint contents and restores their declared state; the runner captures and preserves artifacts and the model/code/configuration/dependency identities needed to load them.
- [§9 Execution](../specs/agentic-ml-harness-design.md#execution) requires cancellation to stop managed training while preserving available checkpoints, restoration metadata, logs, and terminal status under the original run identity. Forced termination does not guarantee a new checkpoint.
- [§10 fixtures](../specs/agentic-ml-harness-design.md#reference-acceptance-test-datasets) and [§11 phase 3](../specs/agentic-ml-harness-design.md#11-phased-implementation-plan) require restoration with verification of usable declared state and preservation checks after cancellation, including forced termination.

Scoped reconciliation on 2026-10-28 against Git revision `4255fdfcd141c70567daf22afbecd3da190328f1` plus this approved working-tree update: the working tree was clean before the correction. US-19-AC-02–03 now have compatible architectural support in Slice 3. User stories and criterion IDs are unchanged. This resolves R-07 as document alignment; implementation and passing tests are not asserted. Exact training continuation is not guaranteed; checkpoint payloads and concrete restore API signatures remain implementation decisions. Review was limited to R-07 and its framework, execution/cancellation, run-evidence, and phase-delivery dependencies. Other criteria were not re-reviewed in full.
