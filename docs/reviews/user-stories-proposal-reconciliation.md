# User Stories and Proposal Reconciliation

## Baseline and scope

- Reviewed on 2026-10-28 at Git revision `dc2a3bc9bff2dfd3070c469b6ef6ca8bac7868b6`.
- Authoritative input: [docs/specs/user-stories.md](../specs/user-stories.md), 30 stories, 35 slice increments, 159 uniquely identified acceptance criteria.
- Supporting input: [proposal version 0.11](../specs/agentic-ml-harness-proposal.md).
- Both complete documents were reviewed. The working tree was clean at baseline. No source-document changes were made; this report is the only generated repository artifact.
- This is architectural document alignment, not a code review or certification that an implementation satisfies these criteria. Pending implementation mechanisms are not automatically coverage failures when their required behavior is otherwise explicit.

The proposal broadly reflects the story outcomes. Alignment is incomplete because its implementation plan postpones some first-slice requirements, and several capture/state assertions need explicit restoration or recovery behavior. One feature-comparison requirement needs a product decision.

## Findings and proposed corrections

### R-01 — High: profiling and split manifests arrive after their required slice

Evidence: [US-12-AC-02](../specs/user-stories.md#us-12-ac-02) requires distributions, class balance, anomalies, and leakage diagnostics in Slice 1; [US-12-AC-03](../specs/user-stories.md#us-12-ac-03) requires a versioned split manifest there. Proposal [§11, line 752](../specs/agentic-ml-harness-proposal.md#11-phased-implementation-plan) places “Profiling, split manifests” in implementation phase 2. Global EDA responsibilities in §3 and the development workflow in §4 support the eventual behavior, but do not resolve the delivery mismatch.

Consequence: the first slice cannot produce its approved dataset assessment and reproducible split protocol as written. Target: proposal §11; retain the story scope.

Proposed addition to phase 1 deliverables:

> Dataset profiling covering distributions, class balance where relevant, anomalies, and leakage diagnostics; versioned train/validation/protected-test split manifests respecting time/group constraints; dataset-assessment and split-protocol review.

Proposed phase 2 change: replace “Profiling, split manifests” with “Consume approved dataset assessments and split manifests from phase 1”. Extend phase 1 exit criteria to require these artifacts and their approval before dependent work.

### R-02 — High: mandatory controls lack an early delivery commitment

Evidence: [US-09-AC-05](../specs/user-stories.md#us-09-ac-05), [US-12-AC-04](../specs/user-stories.md#us-12-ac-04), and [US-26-AC-05](../specs/user-stories.md#us-26-ac-05) require approvals, restrictions, budgets, and independent artifact validation in Slice 1. Baseline approval and protected final evaluation are required in Slice 3; approved agent iteration is required in Slice 4. Proposal §11 [lines 751–755](../specs/agentic-ml-harness-proposal.md#11-phased-implementation-plan) assigns “gates” to phase 5 and does not specify the earlier minimum. §9 describes the final controls, and ADR-006 correctly leaves the isolation mechanism pending, but neither establishes incremental availability.

Consequence: an implementation following the phase table could deliver execution, training, or agent iteration before its mandatory safeguards. Target: proposal §11, with the design constraint recorded under ADR-006; no need to accept a particular isolation implementation now.

Proposed paragraph before the phase table:

> Each implementation phase delivers the controls needed by its corresponding story slice. Phase 1 includes scoped authorization records, execution access restrictions, trial/runtime enforcement, and independent checks of required artifacts. Phase 3 includes baseline approval and independently enforced protected-holdout access with authorized final evaluation and final-model review. Phase 4 uses these controls for approved agent work. Phase 5 adds durable multi-phase coordination, recovery, and a second adapter; it does not introduce the first approval or access checks. The isolation design under ADR-006 must satisfy each control before the capability it protects is delivered.

Add these controls to the corresponding deliverables and exit criteria. Early authorization may be developer-driven; it still must be recorded and enforced.

### R-03 — Medium: the first slice has no explicit agent-free plan-resolution path

Evidence: [US-03-AC-03](../specs/user-stories.md#us-03-ac-03) requires a resolved versioned plan in Slice 1, whose description explicitly excludes an agent. Proposal [§8, line 496](../specs/agentic-ml-harness-proposal.md#developer-experiment-inputs) says “the agent resolves delegated choices”; §4's notebook workflow also assumes an agent. §11 phase 1 promises brief resolution and agent-free execution but leaves the responsible path unspecified.

Consequence: the foundational workflow appears to depend on the phase 4 integration. Target: proposal §8 developer experiment inputs and §11 phase 1.

Proposed addition after the resolution paragraph:

> Before agent integration, developers explicitly supply all required choices. The harness validates and resolves these supplied choices into the same versioned plan, recording defaults, input checksums, and approval evidence. Unresolved delegated choices block dependent execution. Agent-assisted proposals become available in phase 4 and use the same resolution and approval path.

### R-04 — Medium: source capture is stronger than the restoration design

Evidence: [US-13-AC-03](../specs/user-stories.md#us-13-ac-03) requires verified data restoration; [US-27-AC-01–04](../specs/user-stories.md#us-27-ac-01) require second-machine restoration, replay of exact snapshots including uncommitted changes, output checks, and explicit missing-input failures in Slice 1. Proposal §8 installation, §9 tracking, and §12 [lines 449–453, 645–654, and 854](../specs/agentic-ml-harness-proposal.md#experiment-tracking-data-versioning-and-pipelines) describe pinned environments and captured artifacts. §10 includes a clean-environment restoration fixture. These establish intent and inputs, but not the path that assembles them for replay or checks restored content.

Consequence: a complete capture could still be replayed from the wrong working tree or with substituted/missing inputs. Target: proposal §9 and §11 phase 1.

Proposed subsection in §9:

> Restoration uses the recorded run manifest to resolve its pinned harness revision, project lockfile, immutable source/configuration snapshots, runtime guidance where applicable, and DVC dataset identities. Verify recorded source and dataset checksums before execution. Execute the restored snapshots, including preserved uncommitted changes, rather than assuming the Git checkout is the executed source. Missing or mismatched required inputs produce an explicit restoration failure without substitution. Run the recorded entrypoint and compare declared output checks or tolerances; metric tolerances apply when modeling is introduced. Provide an agent-free restoration path and demonstrate it in a clean second-machine environment in phase 1. Exact CLI/API signatures remain pending.

### R-05 — Medium: durable state does not yet explain duplicate-free recovery

Evidence: [US-25-AC-01–02](../specs/user-stories.md#us-25-ac-01), [US-26-AC-13](../specs/user-stories.md#us-26-ac-13), and [US-29-AC-07](../specs/user-stories.md#us-29-ac-07) require reconciliation without duplicated completed runs and preservation of consumed budgets and producer provenance. Proposal [§3 line 101](../specs/agentic-ml-harness-proposal.md#component-responsibilities) assigns durable state and resumption; [§8 line 278](../specs/agentic-ml-harness-proposal.md#8-interfaces-and-contracts) explicitly leaves idempotency design pending; §13 names idempotent jobs and recovery tests. No recovery record or reconciliation behavior is described.

Consequence: a restart between submission and persisted completion can duplicate work, lose budget consumption, or detach reused evidence from its producer. Target: proposal §9 workflow states and §8 contracts.

Proposed addition:

> Durable workflow records preserve phase/configuration identity, task-to-run associations, approvals, evidence/artifact references, consumed budgets, and terminal outcomes. Recovery reconciles these records with runner and tracking status before issuing new work. Completed run identities are reused; ambiguous in-flight work enters review rather than being blindly resubmitted. Resumption preserves producer provenance and consumed budgets and never treats a restart as new authorization. Define the submission/idempotency protocol and interruption tests during phase 5 interface design.

This states the required behavior without selecting a database or transaction implementation.

### R-06 — Medium: the Slice 2 feature-comparison measure needs a story decision

Evidence: [US-14-AC-03](../specs/user-stories.md#us-14-ac-03) requires comparing feature sets “against a fixed baseline using the same approved validation protocol.” Proposal [§7 line 264](../specs/agentic-ml-harness-proposal.md#7-feature-engineering) repeats the comparison, while §11 phases 2 and 3 separate feature comparison from model adapters and baseline training. Neither document identifies whether this comparison measures feature/data quality or predictive performance.

Consequence: predictive comparison may require a minimal model baseline in Slice 2; a non-model comparison can remain within the existing sequence. Target: story criterion first, then proposal §7/§11. This is an ambiguity, not a demonstrated contradiction or authorization to move all modeling earlier.

Decision needed: choose one of the following criterion clarifications, preserving ID `US-14-AC-03`:

- Feature/data-quality comparison: “Candidate feature sets are compared against a fixed baseline using declared feature-quality checks on the same approved split protocol. Predictive-performance comparison is added in Slice 3.”
- Predictive comparison: “Candidate feature sets are compared using a fixed approved reference estimator, metric, and split protocol. Slice 2 includes the minimal training/evaluation capability needed for this comparison; broader model experimentation remains in Slice 3.”

Do not apply either alternative until the user selects it.

### R-07 — Medium: checkpoint restoration is not specified separately from final-model persistence

Evidence: [US-19-AC-02](../specs/user-stories.md#us-19-ac-02) requires captured checkpoints that the model implementation can restore, and [US-19-AC-03](../specs/user-stories.md#us-19-ac-03) requires cancellation to preserve available checkpoints. Proposal [§3 line 108](../specs/agentic-ml-harness-proposal.md#component-responsibilities) and [§9 line 632](../specs/agentic-ml-harness-proposal.md#execution) capture checkpoints; the ModelAdapter saves/loads fitted models. Capturing checkpoints and loading a final model do not by themselves explain checkpoint restoration or cancellation preservation.

Consequence: an adapter may satisfy final-model persistence while offering no usable checkpoint restore path. Target: proposal §8 framework capabilities, §9 execution, and §11 phase 3.

Proposed addition:

> PyTorch integrations preserve emitted checkpoints as run artifacts with the model/code/configuration identities needed to restore them through the supplied or built-in model implementation. Cancellation preserves already available checkpoints, logs, and terminal status; it does not promise a new checkpoint after forced termination. Phase 3 verification includes restoring a captured checkpoint and inspecting artifacts after cancellation. Exact checkpoint payloads remain framework-specific.
